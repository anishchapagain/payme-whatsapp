Section 1 • Internal Payme Server Architecture

How the Payme Server Internally Receives, Queues, Processes, and Sends WhatsApp Messages

In production, your Payme server should never execute slow database queries, FX quote locks, or outbound HTTP calls synchronously inside the webhook HTTP handler. Meta's WhatsApp Cloud API expects a `200 OK` response rapidly; if your endpoint blocks or times out, Meta retries the same webhook with exponential backoff, causing duplicate messages to the user.

To guarantee zero duplicate messages, strict ordering when a user double-taps buttons, and sub-second responsiveness, split your Payme WhatsApp backend into 4 internal tiers shown in the architecture diagram below:

Figure 1.1 — Payme Internal Server Architecture separating Fast-Ack Webhook Ingress, BullMQ Worker Queues, Redis 2-Hour Hot State, PostgreSQL 16 Persistent Tables, and the Window-Aware Outbound Dispatcher.

1. Fast-Ack & Deduplication

  • Meta retries any webhook that takes >5–10s or returns non-2xx.
  • Your ingress route verifies X-Hub-Signature-256, executes SET payme:wa:dedup:{wamid} 1 EX 86400 NX in Redis, pushes the payload to BullMQ, and immediately returns 200 OK in under 100ms.
  • If SETNX returns null, the webhook is a duplicate retry and is safely ignored.

2. Per-User Mutex Lock

  • Users on mobile frequently double-tap interactive buttons (e.g., tapping "Bank Deposit" twice in 200ms).
  • Before processing a job for wa_phone, the worker acquires a Redis lock (payme:wa:lock:{wa_phone}, TTL 5000ms) so the second tap waits until the first state transition commits.

3. Window-Aware Outbound Queue

  • Every inbound user message updates wa_conversations.service_window_expires_at = NOW() + INTERVAL '24 hours' (Meta Service Window).
  • Before sending any outbound message, the dispatcher checks if service_window_expires_at > NOW(). If open, it sends free-form interactive/text JSON; if expired, it automatically wraps the notification in an approved template.

Redis Key Pattern Redis Type TTL Purpose & Stored Value Structure
payme:wa:session:{wa_phone} STRING (JSON) 7200s (2 Hours) Hot cache of the active `wa_sessions` record. Read on every webhook in `<1ms`; write-through to PostgreSQL `wa_sessions` on step change.
payme:wa:handoff:{ref_id} STRING (JSON) 900s (15 Mins) Stores `{ webUserId, corridor, sendAmountUsd }` minted when clicking "Send via WhatsApp" on `payme.com`. Deleted via `GETDEL` on first webhook.
payme:wa:flow_token:{flow_token} STRING 7200s (2 Hours) Maps `flow_token` → `session_id` + `wa_phone` so `/api/wa/flows-endpoint` validates that a WhatsApp Flow form belongs to an active 2-hour session.
payme:wa:dedup:{wamid} STRING 86400s (24 Hours) Set via `SET key 1 EX 86400 NX` at webhook ingress to guarantee idempotent processing if Meta retries a webhook.
payme:wa:lock:{wa_phone} STRING 5000ms (5 Seconds) Per-user distributed mutex lock (`SET key worker_id PX 5000 NX`) so rapid double-taps by the same user are serialized in order.
Section 4 • Runtime Conditions & Guardrails Specification

The 24 Server Conditions Required to Receive, Validate, and Send Messages Safely

Filter the conditions matrix below by subsystem to review every validation rule, SQL/Redis check, and fallback action your development team should implement in the Payme Server.

ID & Category Condition / Trigger Server Check (Redis / SQL / Crypto) System Action & User Experience
C-01
Ingress		 Invalid Webhook HMAC Signature HMAC_SHA256(rawBody, APP_SECRET) !== req.headers['x-hub-signature-256'] Reject immediately with HTTP 401 Unauthorized; do not enqueue or touch DB.
C-02
Ingress		 Duplicate Webhook Delivery (Meta Retry) redis.set(`payme:wa:dedup:${wamid}`, '1', 'EX', 86400, 'NX') === null Return HTTP 200 OK immediately and drop event so user never receives duplicate bot replies.
C-03
Ingress		 Concurrent Double-Tap by Same User redis.set(`payme:wa:lock:${wa_phone}`, jobId, 'PX', 5000, 'NX') === null Worker delays job by 300ms and retries lock acquisition so state transitions execute strictly sequentially.
C-04
Ingress		 Stale / Out-of-Order Webhook Timestamp message.timestamp < wa_conversations.last_inbound_at Log in wa_message_logs for audit but do not regress wa_sessions.current_step.
C-05
Security		 User Types Raw Credit/Debit Card Number in Chat Regex /\b(?:\d[ -]*?){13,19}\b/ + Luhn check on messages[0].text.body Mask digits as [REDACTED_PAN] before writing to wa_message_logs.payload_json; send warning that card details are only accepted in the secure WebView.
C-06
Crypto		 WhatsApp Flow RSA/AES Decryption Failure privateDecrypt or AESGCM.decrypt throws exception on /api/wa/flows-endpoint Return HTTP 421 Misdirected Request (Meta Flow Spec) so WhatsApp client automatically re-downloads your public key.
C-07
Session		 First Website Click (`[Ref: PMW-xxxxxx]`) GETDEL payme:wa:handoff:PMW-xxxxxx returns valid JSON & no active session exists Create new 2-hour session (EX 7200), bind web_user_id/corridor/amount to wa_phone, and jump straight to Delivery Mode (if amount+corridor present) or Country List.
C-08
Session		 Expired or Replay Website Handoff Token GETDEL payme:wa:handoff:PMW-xxxxxx returns null (expired >15m or already used) Do not fail; gracefully start a standard 2-hour session at AWAITING_CORRIDOR and greet the user.
C-09
Re-Entry		 User Re-Clicks Website Link Within 2 Hours (Draft In Progress) wa_sessions.expires_at > NOW() AND current_step NOT IN ('IDLE','COMPLETED','EXPIRED') Save new web parameters in pending_web_context, set step to AWAITING_RESUME_DECISION, and send 2 buttons: ▶️ Resume Current vs. 🔄 Start New Transfer.
C-10
Re-Entry		 User Re-Clicks Website Link After 2 Hours (>7200s) Redis key payme:wa:session:{wa_phone} missing OR wa_sessions.expires_at <= NOW() Mark old DB row current_step = 'EXPIRED', expire old quote, create a fresh session_id with a new 2-hour TTL, and fetch live FX rates.
C-11
Re-Entry		 User Re-Clicks Website Link After Completing Payment wa_sessions.current_step = 'COMPLETED' and wa_conversations.last_paid_tx_id IS NOT NULL Send Interactive Buttons offering 💸 Send Another Transfer (mints new 2h session) or 📦 Track Transfer {MTCN}.
C-12
Flow Token		 User Submits an Old WhatsApp Flow Form from Chat History nfm_reply.flow_token !== active_session.flow_token OR session expired Reject stale form submission and send a 1-tap button to launch a fresh form with current FX rates.
C-13
FX Quote		 Invalid or Out-of-Range Send Amount Parsed USD amount is NaN, < $1.00, or > $999.99 (including fee) Keep current_step = 'AWAITING_AMOUNT' and prompt user to enter an amount between $1.00 and $999.99 USD (Ria WhatsApp Limit).
C-14
FX Quote		 15-Minute FX Rate Lock Expired Before Payment fx_quotes.locked_until < NOW() when user opens WebView or requests checkout link Automatically recalculate quote using current corridor FX rate, update quote_id, and show updated payout amount for 1-tap confirmation.
C-15
Velocity		 Daily ($999.99) or Monthly ($7,999.99) WhatsApp Limit Exceeded SELECT SUM(send_amount_usd) FROM remittance_transactions WHERE user_id = $1 AND created_at > NOW() - INTERVAL '24 hours' Block draft creation in chat and send a polite message explaining the remaining daily/monthly WhatsApp allowance (with link to full Web/App for higher-tier limits).
C-16
Identity		 WhatsApp Phone Matches Existing Payme User vs. New Prospect SELECT id, kyc_tier FROM users WHERE phone_e164 = $1 If found, link wa_conversations.user_id and load saved beneficiaries; if not found, create a shadow/prospect user record and require KYC WebView before payment.
C-17
KYC Gate		 User KYC Unverified or Expired ID Document users.kyc_tier = 'T0' OR kyc_verifications.kyc_status != 'APPROVED' Transition session to AWAITING_KYC_WEBVIEW and send signed cta_url to existing Payme KYC WebView. Do not generate payment link until kyc.approved webhook fires.
C-18
Beneficiary		 Bank Account / CLABE Checksum or Name Validation Fails Payme Beneficiary Service returns validation error during Flow data_exchange Return the same SCREEN_BENEFICIARY in Flow response with field-level error_message so the user fixes the typo inside the form without closing it.
C-19
Reg E		 30-Minute Statutory Cancellation Request User taps "Cancel Transfer" within 30 mins of payment AND payout_status = 'QUEUED' Call existing Payme Refund API, void/refund the 3DS2 card charge, update payment_status = 'REFUNDED', and push cancellation confirmation in WhatsApp.
C-20
Window		 Outbound Message Inside 24-Hour Customer Service Window wa_conversations.service_window_expires_at > NOW() Send dynamic type: "interactive" (List, Reply Buttons, Flow, CTA URL) or type: "text" directly via POST /{PHONE_ID}/messages.
C-21
Window		 Outbound Message Outside 24-Hour Window (e.g., Delayed Bank Payout) wa_conversations.service_window_expires_at <= NOW() Must send type: "template" using an APPROVED template from wa_template_registry (e.g., payme_transfer_receipt or payme_payout_status_update).
C-22
WebView		 KYC Approved Event Received from Existing Payme Backend POST /webhooks/payme-core with event = 'kyc.approved' Update wa_sessions.current_step = 'AWAITING_PAYMENT_WEBVIEW' and automatically push the signed 3DS2 Payment Checkout cta_url button to WhatsApp.
C-23
WebView		 Payment Captured Event Received from Existing Payme Backend POST /webhooks/payme-core with event = 'payment.captured' Mark wa_sessions.current_step = 'COMPLETED', set wa_conversations.last_paid_tx_id, and push the confirmation receipt with mtcn_reference + 🔄 Check Status button.
C-24
Rate Limit		 Meta Cloud API Throughput / HTTP 429 Error Meta returns error 130429 (Rate limit hit) or 503 BullMQ Outbound Worker retries with exponential backoff (1s, 2s, 4s, 8s) preserving message order per wa_phone.

Reference Implementation: Fast-Ack Ingress, Mutex Worker, and Window-Aware Dispatcher

src/api/whatsappWebhookIngress.ts (HMAC Verification + Redis Dedup + BullMQ Enqueue) 
import crypto from "node:crypto";
import express, { Request, Response } from "express";
import { Queue } from "bullmq";
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL!);
const inboundQueue = new Queue("payme-wa-inbound", { connection: redis });
export const ingressRouter = express.Router();

// Condition C-05: Redact any accidental 13-19 digit card PANs before logging
function redactSensitivePan(rawJson: string): string {
  return rawJson.replace(/\b(?:\d[ -]*?){13,19}\b/g, "[REDACTED_PAN]");
}

ingressRouter.post(
  "/webhooks/whatsapp",
  express.raw({ type: "application/json" }),
  async (req: Request, res: Response) => {
    // Condition C-01: Verify X-Hub-Signature-256 over raw request bytes
    const sigHeader = req.get("x-hub-signature-256") || "";
    const expectedSig =
      "sha256=" +
      crypto
        .createHmac("sha256", process.env.WHATSAPP_APP_SECRET!)
        .update(req.body)
        .digest("hex");

    if (
      sigHeader.length !== expectedSig.length ||
      !crypto.timingSafeEqual(Buffer.from(sigHeader), Buffer.from(expectedSig))
    ) {
      return res.status(401).send("Invalid signature");
    }

    const payload = JSON.parse(req.body.toString("utf-8"));
    const value = payload?.entry?.[0]?.changes?.[0]?.value;

    // Acknowledge Meta immediately (<100ms) so Meta never retries
    res.status(200).send("EVENT_RECEIVED");

    // Handle Inbound User Message (text, list_reply, button_reply, nfm_reply)
    const msg = value?.messages?.[0];
    if (msg) {
      const wamid: string = msg.id;
      // Condition C-02: Atomic 24-hour idempotency check in Redis
      const isNew = await redis.set(`payme:wa:dedup:${wamid}`, "1", "EX", 86400, "NX");
      if (!isNew) return; // Duplicate retry from Meta — ignore safely

      await inboundQueue.add(
        "process-inbound-msg",
        {
          waPhone: msg.from,
          profileName: value?.contacts?.[0]?.profile?.name || "Customer",
          message: JSON.parse(redactSensitivePan(JSON.stringify(msg))),
        },
        { removeOnComplete: 1000, attempts: 3, backoff: { type: "exponential", delay: 500 } }
      );
    }

    // Handle Delivery Status Updates (sent, delivered, read, failed)
    const statusEvent = value?.statuses?.[0];
    if (statusEvent) {
      await inboundQueue.add("update-msg-status", {
        wamid: statusEvent.id,
        status: statusEvent.status.toUpperCase(),
        errorCode: statusEvent.errors?.[0]?.code || null,
      });
    }
  }
);
src/workers/inboundStateWorker.ts (Per-User Mutex Lock + DB/Redis 2-Hour Session Sync) 
import { Worker, Job } from "bullmq";
import { Pool } from "pg";
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL!);
const pgPool = new Pool({ connectionString: process.env.DATABASE_URL });
const TWO_HOURS_SEC = 7200;

export const inboundWorker = new Worker(
  "payme-wa-inbound",
  async (job: Job) => {
    if (job.name === "update-msg-status") {
      const { wamid, status, errorCode } = job.data;
      await pgPool.query(
        `UPDATE wa_message_logs
         SET delivery_status = $1, meta_error_code = $2, status_updated_at = NOW()
         WHERE wamid = $3`,
        [status, errorCode, wamid]
      );
      return;
    }

    const { waPhone, profileName, message } = job.data;
    const lockKey = `payme:wa:lock:${waPhone}`;

    // Condition C-03: Acquire per-user mutex lock (5s) to serialize double-taps
    const lockAcquired = await redis.set(lockKey, job.id!, "PX", 5000, "NX");
    if (!lockAcquired) {
      throw new Error("USER_LOCK_BUSY_RETRY"); // BullMQ retries after backoff
    }

    const client = await pgPool.connect();
    try {
      await client.query("BEGIN");

      // 1. Upsert wa_conversations & extend 24-hour Meta Customer Service Window
      await client.query(
        `INSERT INTO wa_conversations (wa_phone, wa_profile_name, service_window_expires_at, last_inbound_at)
         VALUES ($1, $2, NOW() + INTERVAL '24 hours', NOW())
         ON CONFLICT (wa_phone) DO UPDATE SET
           wa_profile_name = EXCLUDED.wa_profile_name,
           service_window_expires_at = NOW() + INTERVAL '24 hours',
           last_inbound_at = NOW(),
           updated_at = NOW()`,
        [waPhone, profileName]
      );

      // 2. Log inbound message in wa_message_logs
      await client.query(
        `INSERT INTO wa_message_logs (wamid, wa_phone, direction, msg_type, payload_json)
         VALUES ($1, $2, 'INBOUND', $3, $4)
         ON CONFLICT (wamid) DO NOTHING`,
        [message.id, waPhone, message.interactive?.type || message.type, JSON.stringify(message)]
      );

      // 3. Load active 2-hour session from Redis (or fallback to PostgreSQL)
      const sessionKey = `payme:wa:session:${waPhone}`;
      let sessionRaw = await redis.get(sessionKey);
      let session = sessionRaw ? JSON.parse(sessionRaw) : null;

      if (!session) {
        const dbSess = await client.query(
          `SELECT * FROM wa_sessions
           WHERE wa_phone = $1 AND expires_at > NOW()
             AND current_step NOT IN ('COMPLETED', 'EXPIRED', 'CANCELLED')
           ORDER BY created_at DESC LIMIT 1`,
          [waPhone]
        );
        session = dbSess.rows[0] || null;
      }

      // 4. Execute state transition & enqueue outbound WhatsApp JSON response
      const updatedSession = await evaluateStateTransition(client, redis, waPhone, message, session);

      // 5. Refresh 2-hour (7200s) TTL in both Redis and PostgreSQL
      await redis.set(sessionKey, JSON.stringify(updatedSession), "EX", TWO_HOURS_SEC);
      await client.query(
        `UPDATE wa_sessions
         SET current_step = $1, corridor_code = $2, send_amount_usd = $3,
             delivery_mode = $4, quote_id = $5, beneficiary_id = $6,
             draft_tx_id = $7, expires_at = NOW() + INTERVAL '2 hours', updated_at = NOW()
         WHERE session_id = $8`,
        [
          updatedSession.current_step,
          updatedSession.corridor_code,
          updatedSession.send_amount_usd,
          updatedSession.delivery_mode,
          updatedSession.quote_id,
          updatedSession.beneficiary_id,
          updatedSession.draft_tx_id,
          updatedSession.session_id,
        ]
      );

      await client.query("COMMIT");
    } catch (err) {
      await client.query("ROLLBACK");
      throw err;
    } finally {
      client.release();
      await redis.del(lockKey); // Release per-user mutex
    }
  },
  { connection: redis, concurrency: 20 }
);
src/workers/outboundWhatsAppDispatcher.ts (24-Hour Window Check + Template Fallback) 
import { Worker, Job } from "bullmq";
import { Pool } from "pg";
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL!);
const pgPool = new Pool({ connectionString: process.env.DATABASE_URL });

export const outboundDispatcher = new Worker(
  "payme-wa-outbound",
  async (job: Job) => {
    const { waPhone, sessionId, payload, fallbackTemplate } = job.data;

    // Conditions C-20 & C-21: Check if the 24-hour Customer Service Window is currently open
    const convRes = await pgPool.query(
      `SELECT service_window_expires_at > NOW() AS window_open
       FROM wa_conversations WHERE wa_phone = $1`,
      [waPhone]
    );
    const windowOpen = convRes.rows[0]?.window_open === true;

    // If 24h window is closed and payload is not already a template, switch to fallbackTemplate
    const bodyToSend =
      !windowOpen && payload.type !== "template" && fallbackTemplate
        ? fallbackTemplate
        : payload;

    const response = await fetch(
      `https://graph.facebook.com/v23.0/${process.env.WHATSAPP_PHONE_NUMBER_ID}/messages`,
      {
        method: "POST",
        headers: {
          Authorization: `Bearer ${process.env.WHATSAPP_SYSTEM_USER_TOKEN}`,
          "Content-Type": "application/json",
        },
        body: JSON.stringify({
          messaging_product: "whatsapp",
          recipient_type: "individual",
          to: waPhone,
          ...bodyToSend,
        }),
      }
    );

    if (response.status === 429 || response.status >= 500) {
      // Condition C-24: Trigger BullMQ exponential backoff retry
      throw new Error(`META_API_TRANSIENT_${response.status}`);
    }

    const resData = await response.json();
    const outWamid = resData?.messages?.[0]?.id || `local_${Date.now()}`;

    // Persist outbound message in wa_message_logs for compliance & delivery status tracking
    await pgPool.query(
      `INSERT INTO wa_message_logs
         (wamid, wa_phone, session_id, direction, msg_type, template_name, payload_json, delivery_status)
       VALUES ($1, $2, $3, 'OUTBOUND', $4, $5, $6, 'SENT')`,
      [
        outWamid,
        waPhone,
        sessionId || null,
        bodyToSend.type === "interactive" ? bodyToSend.interactive.type : bodyToSend.type,
        bodyToSend.template?.name || null,
        JSON.stringify(bodyToSend),
      ]
    );
  },
  { connection: redis, concurrency: 15 }
);

Where & How AI Is Used in Payme's WhatsApp Remittance Flow

Engineering Principle: "AI Suggests, Deterministic State Machine Commits"
Inspired by Félix Pago and Remitly, AI is never allowed to invent exchange rates, calculate fees, bypass KYC, or execute payments. Instead, AI acts as an unstructured-to-structured input parser and support copilot across 4 areas:

1. Voice-Note & Free-Text Intent Extraction (NLU)

  • Trigger: User sends a WhatsApp voice note (type: "audio") or natural text such as "Send $400 to my brother Ramesh in Nepal via bank deposit".
  • Pipeline: Transcribe audio via OpenAI Whisper / Deepgram → parse with Gemini / GPT-4o Structured Outputs into { corridor: "NP", send_amount_usd: 400, delivery_mode: "BANK_DEPOSIT", beneficiary_hint: "Ramesh" }.
  • Handoff: Pre-populates wa_sessions, locks the real quote via Payme's FX API, and jumps straight to confirmation.

2. Vision OCR for Bank Slips & Check Photos

  • Trigger: User uploads a photo of a handwritten bank account number, passbook, or 18-digit Mexican CLABE / Indian IFSC card in WhatsApp.
  • Pipeline: Multimodal Vision model extracts { bank_name, account_number, routing_code, account_holder } and pre-fills SCREEN_BENEFICIARY in the WhatsApp Flow via flow_action_data.
  • Handoff: User verifies pre-filled fields in the native Flow form and Payme's Bank Validation API confirms the account.

3. Multilingual RAG Support Copilot (Mid-Flow FAQ)

  • Trigger: User asks a question mid-flow (e.g., "What ID does my recipient need at Elektra?" or "Why is my transfer pending?").
  • Pipeline: Answers from Payme's verified Corridor Knowledge Base and live GET /v1/remittances/{id}/status API, then appends a ▶️ Resume Transfer button so the 2-hour session never drops.

4. Conversational Fraud & Coercion Scoring

  • Trigger: Evaluated asynchronously before minting the signed 3DS2 Payment Checkout URL.
  • Pipeline: Flags high-risk scam patterns (new beneficiary + uncharacteristic corridor + urgent coaching cues) and triggers an in-chat scam warning or step-up liveness check.
