Crucial Architectural Insight: "WhatsApp Templates" vs. Interactive Messages vs. WhatsApp Flows
When users interact with Ria, Félix Pago, or Remitly on WhatsApp, what looks like a "template" to collect amount, beneficiary, and delivery options is actually a combination of three distinct Meta Cloud API primitives (Meta Service & Interactive Messages Docs):
  1. Message Templates (type: "template"): Require prior Meta approval (Template Fundamentals). Used to initiate messages outside the 24-hour customer service window (e.g., FX rate alerts, abandoned transfer nudges, or pushing a confirmed UTILITY transfer receipt / cash pickup PIN) OR to attach a FLOW button to an outbound campaign.
  2. Free-Form Interactive Messages (type: "interactive"): Require zero Meta approval and are free to send within 24 hours of the user's last message (Interactive Message API Library). Includes Interactive List Menus (up to 10 rows for choosing Country or Saved Beneficiary), Reply Buttons (up to 3 quick-tap buttons for Bank Deposit, Cash Pickup, Wallet), and CTA URL Buttons (cta_url for opening Payme's KYC or Payment Checkout URL).
  3. WhatsApp Flows (interactive.type: "flow"): Meta's native in-app form engine (WhatsApp Flows Overview). Renders rich multi-screen forms (Dropdowns, TextInputs, RadioButtons, DatePickers) inside a native slide-up drawer. Connected to Payme's backend via an encrypted data_exchange endpoint (Flow JSON v7.0) to validate bank accounts, fetch live FX quotes, and create beneficiaries without leaving WhatsApp.

How Server JSON Is Sent to WhatsApp & How User Responses Return to Your Server

Your architectural assumption—(1) User opens WhatsApp from a link on Payme's website → (2) Meta WhatsApp Cloud API → (3) Existing Payme Server processes each step, hands off to existing KYC & Payment web pages (in-app WebView), and pushes the final Confirmation + Payment ID + Tracking back to WhatsApp—is 100% the industry-standard architecture used by Ria Money Transfer and Remitly.

Key Technical Distinction: Pre-Approved Templates vs. Real-Time Interactive JSON
  • When the user clicks the WhatsApp link on Payme's website (https://wa.me/18005550199?text=Send%20Money): The user sends the first message, which automatically opens a free 24-hour Customer Service Window (Meta Service Messages Docs).
  • During this 24-hour window, you do NOT need pre-approved Message Templates for every chat question: Instead, your Payme server dynamically sends JSON payloads (type: "interactive" or type: "text") directly to POST /{PHONE_NUMBER_ID}/messages to ask for Country, Send Amount, Delivery Mode, and Beneficiary details.
  • When ARE Pre-Approved Message Templates (type: "template") used? Templates (built either in the Meta WhatsApp Manager UI or via POST /{WABA_ID}/message_templates JSON API) are used when your server initiates contact outside the 24-hour window OR for guaranteed transactional delivery such as the Post-Payment Confirmation Receipt & Payment ID and asynchronous Payout Status Alerts.

Section 5C • Website Click Handoff, 2-Hour Session TTL & Re-Entry Logic

What Happens on First Website Click, How 2-Hour Sessions Work, and What Happens on Re-Click

When a customer clicks "Send via WhatsApp" on payme.com, you bridge an unauthenticated or logged-in browser session into a stateful, 2-hour (`7,200-second`) conversational remittance instance keyed by the user's verified WhatsApp phone number (`wa_id`).

1. Step-by-Step: What Happens When the User First Clicks "Send via WhatsApp" on Payme's Website?

Step 1A: Website Mints a Pre-Seeded Handoff Token

  • When the user clicks "Send via WhatsApp" on payme.com (optionally after picking a country/amount on your website calculator), your frontend calls POST /v1/wa-handoff/init on the Payme server.
  • Your server creates a temporary handoff record in Redis (TTL: 15 mins) with a short reference ID such as PMW-9F3K82 storing any website context (e.g., web_user_id if logged in, corridor: "NP", amount_usd: 500).
  • The website opens the official WhatsApp Universal Click-to-Chat URL (Meta Click-to-Chat):
    https://wa.me/18005550199?text=Start%20Payme%20Transfer%20%5BRef%3A%20PMW-9F3K82%5D

Step 1B: User Taps Send → Meta Fires Inbound Webhook

  • On mobile, the OS launches the WhatsApp app directly into the verified Payme Money Transfer chat with the message box pre-filled: Start Payme Transfer [Ref: PMW-9F3K82]. (On desktop, you can also display a QR code of that exact wa.me link).
  • The moment the user taps Send (➤), WhatsApp delivers the message to Meta Cloud API, which immediately sends an HTTP POST webhook to your Payme server.
  • Your server extracts PMW-9F3K82, links the website context to the user's WhatsApp phone number (messages[0].from), and creates the 2-hour active session.

// 2. CALLED BY WHATSAPP WEBHOOK WHEN USER CLICKS WEBSITE LINK (FIRST TIME OR RE-CLICK)
export async function handleWebsiteEntryWebhook(message, redis, paymeCoreApi) {
  const waPhone = message.from; // e.g., "17135550142"
  const text = message.text?.body || "";
  const refMatch = text.match(/\[Ref:\s*(PMW-[A-F0-9]+)\]/i);

  // Consume single-use website handoff token if present
  let webContext = null;
  if (refMatch) {
    const handoffKey = `payme:wa:handoff:${refMatch[1].toUpperCase()}`;
    const rawHandoff = await redis.get(handoffKey);
    if (rawHandoff) {
      webContext = JSON.parse(rawHandoff);
      await redis.del(handoffKey); // Single-use nonce
    }
  }

  // Check if an active 2-hour session already exists for this WhatsApp phone number
  const sessionKey = `payme:wa:session:${waPhone}`;
  const existingRaw = await redis.get(sessionKey);
  const existingSession = existingRaw ? JSON.parse(existingRaw) : null;

  // SCENARIO A: User has an unfinished in-progress session (< 2 hours old)
  if (existingSession && existingSession.step !== "IDLE" && existingSession.step !== "COMPLETED") {
    // Store the new webContext as a pending option in case they choose "Start Fresh"
    existingSession.pendingWebContext = webContext;
    await redis.set(sessionKey, JSON.stringify(existingSession), "EX", TWO_HOURS_SECONDS);

    return sendWhatsAppJson(waPhone, {
      type: "interactive",
      interactive: {
        type: "button",
        header: { type: "text", text: "Unfinished Transfer Found ⏳" },
        body: {
          text: `You have an active transfer in progress (${existingSession.amountUsd ? "$" + existingSession.amountUsd + " USD" : "Draft"} to ${existingSession.corridor || "recipient"}).\n\nWould you like to resume where you left off or start a new transfer?`
        },
        footer: { text: "Active session valid for 2 hours" },
        action: {
          buttons: [
            { type: "reply", reply: { id: "session_RESUME", title: "▶️ Resume Current" } },
            { type: "reply", reply: { id: "session_RESTART", title: "🔄 Start New Transfer" } }
          ]
        }
      }
    });
  }

  // SCENARIO B & C: No active session (First click, OR >2h expired, OR previous was COMPLETED)
  const newSession = {
    sessionId: `sess_${crypto.randomUUID()}`,
    waPhone,
    webUserId: webContext?.webUserId || existingSession?.webUserId || null,
    corridor: webContext?.corridor || null,
    amountUsd: webContext?.sendAmountUsd || null,
    step: webContext?.corridor && webContext?.sendAmountUsd
      ? "AWAITING_DELIVERY_MODE"
      : "AWAITING_CORRIDOR",
    createdAt: Date.now(),
    expiresAt: Date.now() + TWO_HOURS_SECONDS * 1000,
  };

  // Save with 2-hour (7200s) TTL in Redis
  await redis.set(sessionKey, JSON.stringify(newSession), "EX", TWO_HOURS_SECONDS);

  // If website already passed corridor & amount (e.g., $500 to NP), skip straight to Delivery Method!
  if (newSession.step === "AWAITING_DELIVERY_MODE") {
    const quote = await paymeCoreApi.post("/v1/quotes", {
      corridor: newSession.corridor,
      sendAmountUsd: newSession.amountUsd,
    });
    newSession.quoteId = quote.id;
    newSession.payoutFormatted = quote.payoutFormatted;
    await redis.set(sessionKey, JSON.stringify(newSession), "EX", TWO_HOURS_SECONDS);

    return sendWhatsAppJson(waPhone, {
      type: "interactive",
      interactive: {
        type: "button",
        header: { type: "text", text: "Payme Quote Loaded from Website ✅" },
        body: {
          text: `We loaded your website selection:\n• Send: *$${newSession.amountUsd} USD*\n• Receive: *${quote.payoutFormatted}* (${newSession.corridor})\n\nSelect how your recipient will receive the money:`
        },
        action: {
          buttons: [
            { type: "reply", reply: { id: "mode_BANK_DEPOSIT", title: "🏦 Bank Deposit" } },
            { type: "reply", reply: { id: "mode_CASH_PICKUP", title: "💵 Cash Pickup" } }
          ]
        }
      }
    });
  }

  // Otherwise start at Step 1 (Select Country List)
  return sendCorridorListMenu(waPhone);
}

// Decrypt incoming request from Meta WhatsApp Flows
function decryptFlowRequest(body, privatePem, passphrase) {
  const { encrypted_aes_key, encrypted_flow_data, initial_vector } = body;

  const privateKey = crypto.createPrivateKey({
    key: privatePem,
    format: "pem",
    passphrase,
  });

  // 1. Unwrap the 128-bit AES key using RSA-OAEP with SHA-256
  const decryptedAesKey = crypto.privateDecrypt(
    {
      key: privateKey,
      padding: crypto.constants.RSA_PKCS1_OAEP_PADDING,
      oaepHash: "sha256",
    },
    Buffer.from(encrypted_aes_key, "base64")
  );

  // 2. Split encrypted_flow_data into Ciphertext and 16-byte GCM Auth Tag
  const flowDataBuffer = Buffer.from(encrypted_flow_data, "base64");
  const ivBuffer = Buffer.from(initial_vector, "base64");
  const TAG_LENGTH = 16;
  const encryptedBody = flowDataBuffer.subarray(0, -TAG_LENGTH);
  const authTag = flowDataBuffer.subarray(-TAG_LENGTH);

  // 3. Decrypt payload using AES-128-GCM
  const decipher = crypto.createDecipheriv("aes-128-gcm", decryptedAesKey, ivBuffer);
  decipher.setAuthTag(authTag);
  const decryptedJsonString = Buffer.concat([
    decipher.update(encryptedBody),
    decipher.final(),
  ]).toString("utf-8");

  return {
    decryptedBody: JSON.parse(decryptedJsonString),
    aesKeyBuffer: decryptedAesKey,
    ivBuffer,
  };
}

// Encrypt outgoing screen response using bitwise-inverted IV (~iv)
function encryptFlowResponse(responsePayload, aesKeyBuffer, ivBuffer) {
  // Flip every byte of the initial_vector using bitwise NOT
  const flippedIv = Buffer.alloc(ivBuffer.length);
  for (let i = 0; i < ivBuffer.length; i++) {
    flippedIv[i] = ~ivBuffer[i] & 0xff;
  }

  const cipher = crypto.createCipheriv("aes-128-gcm", aesKeyBuffer, flippedIv);
  const plaintext = JSON.stringify(responsePayload);
  const encrypted = Buffer.concat([
    cipher.update(plaintext, "utf-8"),
    cipher.final(),
    cipher.getAuthTag(), // Append 16-byte GCM authTag at the end
  ]);

  return encrypted.toString("base64");
}

import json
from fastapi import FastAPI, Request, Response
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

app = FastAPI()

def decrypt_flow_request(payload: dict, private_key_pem: bytes, passphrase: bytes):
    encrypted_flow_data = base64.b64decode(payload["encrypted_flow_data"])
    encrypted_aes_key = base64.b64decode(payload["encrypted_aes_key"])
    initial_vector = base64.b64decode(payload["initial_vector"])

    private_key = serialization.load_pem_private_key(private_key_pem, password=passphrase)

    # 1. Decrypt 128-bit AES key using RSA-OAEP (SHA-256)
    aes_key = private_key.decrypt(
        encrypted_aes_key,
        padding.OAEP(
            mgf=padding.MGF1(algorithm=hashes.SHA256()),
            algorithm=hashes.SHA256(),
            label=None,
        ),
    )

    # 2. Decrypt Flow payload using AES-GCM (includes trailing 16-byte tag)
    aesgcm = AESGCM(aes_key)
    decrypted_bytes = aesgcm.decrypt(initial_vector, encrypted_flow_data, None)
    return json.loads(decrypted_bytes.decode("utf-8")), aes_key, initial_vector

def encrypt_flow_response(response_dict: dict, aes_key: bytes, initial_vector: bytes) -> str:
    # Invert every byte of initial_vector using bitwise NOT (~b & 0xFF)
    flipped_iv = bytes(b ^ 0xFF for b in initial_vector)
    aesgcm = AESGCM(aes_key)
    encrypted_bytes = aesgcm.encrypt(
        flipped_iv,
        json.dumps(response_dict).encode("utf-8"),
        None,
    )
    return base64.b64encode(encrypted_bytes).decode("utf-8")

  }

  if (flowReplyJson) {
    const draft = await paymeCoreApi.post("/v1/remittances/create-from-whatsapp", {

      quoteId: session.quoteId,
      deliveryMode: session.deliveryMode,
      beneficiaryData: flowReplyJson
    });
    session.step = "AWAITING_WEBVIEW_COMPLETION";
    await redis.set(sessionKey, JSON.stringify(session), "EX", 3600);

    // Send Interactive CTA URL Button that opens Payme's KYC & Payment WebView

        },

          }

      }
    });
  }

Section 9 • Security, Compliance & Production Rollout

Regulatory Guardrails, Limits, and Production Go-Live Checklist

Operating a remittance service over WhatsApp requires strict alignment between Meta's Business Messaging Policies, PCI-DSS v4.0, FinCEN/AML KYC rules, and the CFPB Remittance Transfer Rule (Regulation E, Subpart B).

1. Velocity & Tiered Limits

  • Tier 1 (Basic WA Verification): Adopt Ria's WhatsApp guardrail of $999.99/transfer (fees included), $999.99/day, and $7,999.99/month.
  • Debit Card & 3DS2 Enforcement: Restrict initial WhatsApp channel funding to Visa/Mastercard Debit Cards with mandatory 3D Secure 2.0 OTP or verified ACH to prevent credit card chargeback fraud.
  • Phone Number Binding: Match the user's WhatsApp MSISDN (`messages[].from`) against their verified Payme account phone number; require OTP challenge if linking an existing email-only web account.

2. PCI-DSS & PII Isolation

  • Never Accept Card Numbers in Chat: Configure a regex guardrail in your Webhook Orchestrator that detects 13–19 digit Luhn sequences in free text, immediately warns the user, and redacts logs.
  • Encrypted Flows for Beneficiary PII: Collect bank account numbers, CLABEs, and beneficiary ID names inside WhatsApp Flows (`data_exchange`) so sensitive PII is encrypted with your RSA-2048 key and does not sit in plain chat bubbles.
  • Short-Lived Signed Checkout URLs: Mint single-use JWT URLs (`expiresIn: "15m"`) bound to `tx_id` and `wa_id` for your existing Payme Web Checkout.

3. CFPB Reg E & Cancellations

  • Pre-Payment Disclosure: Before sending the `cta_url` payment link, display the exact Send Amount, Front-End Fee, FX Rate, Taxes, and Net Payout to Recipient.
  • Post-Payment Receipt (`UTILITY`): Push `payme_transfer_receipt` containing the reference/MTCN number, promised delivery window, and error-resolution contact details.
  • 30-Minute In-Chat Cancellation: Support a `"Cancel Transfer"` quick-reply button or keyword inside WhatsApp for uncollected transfers within the statutory 30-minute window.
